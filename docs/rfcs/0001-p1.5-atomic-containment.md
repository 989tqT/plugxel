## 1. Executive Summary & Context

Plugxel's P1 release established a robust **defense-in-depth** capability sandbox for WebAssembly plugins (`fs_scoped`):
- Opaque preopened directory mapped to `/data` (`~/.plugxel/data/<plugin_hash>/`)
- Manifest import filtering and runtime descriptor capability checks
- Lexical boundary validation rejecting rooted paths and escaping `..`
- Reparse dereference inhibition at target (`FILE_FLAG_OPEN_REPARSE_POINT` / `O_NOFOLLOW`)
- Kernel handle interrogation post-open (`GetFinalPathNameByHandleW` / `/proc/self/fd/`)
- Deferred truncation (`file.set_len(0)` post-validation) and total elimination of foreign deletion routines

While P1 effectively eliminates accidental leaks and static symlink escapes, it operates on a **check-then-open** + **post-open verification** pattern. This leaves a theoretical TOCTOU race window where a concurrent process or filesystem filter mutates intermediate directory components while resolution is in flight.

The objective of **P1.5** is to eliminate intermediate namespace race windows through:
1. **Atomic kernel-level containment primitives** on Linux (`openat2` with strict resolution flags).
2. **Component-by-component native handle walking and handle-directed mutations** on Windows (`NtCreateFile` + `SetFileInformationByHandle`).

**Scope Boundary**: P1.5 implementations currently exist strictly as experimental vertical spikes isolated behind `#[cfg(test)]`. Production runtime (`plugin_mgr.rs`) remains on the P1 defense-in-depth baseline. P1.5 is **NOT** yet considered production-ready.

## 2. Threat Model & Trust Boundaries

### 2.1 Attacker Profile
An untrusted or compromised WebAssembly plugin executing inside Wasmer Cranelift runtime with `fs_scoped` storage permission, potentially coordinated with concurrent background guest threads or unprivileged host-level filesystem mutations.

### 2.2 Attack Vectors Addressed in P1.5
1. **Intermediate Component Rename Race**:
   An attacker initiates `path_open("subdir/target.txt")`. Between the runtime's component check of `subdir` and the kernel's open, `subdir` is renamed or swapped to point outside `/data`.
2. **Path-Based Unlink / Rmdir Race**:
   Runtime validates that `target_path` is within `/data`, but before `unlink(target_path)` executes, `target_path` or an intermediate parent is swapped to a critical host file.
3. **Multi-Component Directory Creation Escape**:
   Calling `mkdir("a/b/c")` where intermediate components traverse outside the root.
4. **Symlink, Junction, and Magic-Link Traversal Escape**:
   Traversing symlinks, NTFS junctions, or pseudo-filesystem magic links (e.g. Linux `/proc/self/fd/...` or Windows `\??\...`).
5. **Hard-Link Shared Storage Aliasing**:
   An attacker or compromised fixture places an NTFS hard link inside `/data` referencing a sensitive external host file. Because hard links share the underlying MFT file record without setting reparse point attributes, standard symlink checks fail to detect the alias.
6. **Pre-Verification Destructive Side-Effects**:
   `O_CREAT` or `O_TRUNC` racing to create or truncate a host file before handle verification completes.

### 2.3 Trust Boundary: Inode/File-Object Binding vs. Host Namespace Reparenting
Pinned directory descriptors/handles (`parent_dfd` on Linux, `parent_handle` on Windows) bind directly to the underlying filesystem inode/file object in the kernel VFS.
- **Guest Plugin Boundary**: Plugxel's capability sandbox strictly confines untrusted guest plugins and concurrent guest threads against escaping `/data`.
- **Pinned Descriptors**: Eliminate intermediate pathname resolution races for all guest-initiated and unprivileged operations.
- **Host Process Boundary**: If a privileged external host process moves or reparents an ancestor directory of `/data` while resolution or mutation is in flight, the open handle remains bound to that file object. Privileged host processes belong to the host Trusted Computing Base (TCB); protection against host TCB reparenting is outside the guest capability sandbox boundary.

## 3. Non-Negotiable Security Invariants

1. **Strict Tree Confinement**:
   Every filesystem operation executed on behalf of a guest must resolve strictly beneath the directory descriptor capability representing `/data`. Any resolution escaping the tree must fail immediately with `WASI_ENOTCAPABLE` (`76`).
2. **Zero Pre-Verification Side-Effects**:
   No host file outside `/data` may be created, truncated, modified, or deleted even if a concurrent race occurs during resolution. Truncation must be explicitly deferred until after handle authenticity, reparse absence, hard-link count, and boundary checks pass.
3. **Fail-Closed Policy (Deliberate Security Denial)**:
   If atomic containment primitives (e.g. Linux `openat2`) are unavailable, unsupported by the kernel (< 5.6), or blocked by seccomp (`ENOSYS`), the engine strictly denies capability access with `WASI_ENOTCAPABLE` (`76`). This is an intentional security policy decision: because containment cannot be mathematically guaranteed without atomic kernel primitives, Plugxel denies capability access rather than falling back to uncontained path resolution.
4. **Single-Leaf Mutation on Pinned Parent**:
   Mutating operations (`mkdir`, `unlink`, `rmdir`) must never be dispatched with multi-component path strings. The parent directory descriptor must be safely opened and pinned first; the mutation is dispatched strictly as a single leaf component on the verified parent descriptor.
5. **Hard-Link Multi-Alias Rejection**:
   Files with a link count greater than 1 (`n_number_of_links > 1` on Windows, `st_nlink > 1` on Linux) must be rejected with `WASI_ENOTCAPABLE` (`76`) on open and unlink. Private sandbox files never require multi-linking; this guarantees zero host-file alias corruption.
6. **No Universal Race Detector Fallacy**:
   `openat2` returns `EAGAIN` only in specific kernel race scenarios during resolution. It is not an omniscient race detector. Bounded retries must be enforced (1 initial + 3 retries = 4 total attempts); persistent races return WASI `EAGAIN` (`6`) or fail-closed `ENOTCAPABLE` (`76`).

## 4. Linux Architecture & Implementation

### 4.1 Native Primitive: `openat2(2)`
Linux kernel 5.6+ introduces `openat2`:
```c
int openat2(int dirfd, const char *pathname, struct open_how *how, size_t size);
```

#### Mandatory Resolution Flags (`open_how.resolve`):
Plugxel mandates the following resolution flags for all scoped access:
- `RESOLVE_BENEATH`: Prevents resolution from walking outside the directory tree rooted at `dirfd`. Any `..` that would exit `dirfd` or absolute path returns `EXDEV` or `EACCES`.
- `RESOLVE_NO_XDEV` (**Mandated Architectural Decision**): Prohibits traversal across mount points, including bind mounts. When path resolution encounters any mount point during lookup, the kernel immediately halts resolution and returns `EXDEV`. This policy does not claim to prohibit internal filesystem-layer operations that are not mount-point crossings. In Plugxel's capability model, crossing mount boundaries introduces cross-device hardlink/rename anomalies and expands sandbox escape surfaces; `EXDEV` is strictly mapped to `WASI_ENOTCAPABLE` (`76`).
- `RESOLVE_NO_MAGICLINKS`: Blocks traversal of magic links (e.g., `/proc/self/fd/...`).
- `RESOLVE_NO_SYMLINKS`: Disallows symlink traversal completely (aligned with Plug's policy of zero symlink creation).

#### Race Handling:
If the kernel detects a concurrent rename that prevents it from guaranteeing `RESOLVE_BENEATH` containment, it returns `EAGAIN`.
- **Bounded Retry Policy**: Exactly 1 initial attempt plus 3 bounded retries (total 4 attempts) with `std::thread::yield_now()` backoff. If `EAGAIN` persists, return WASI `EAGAIN` (`6`).

### 4.2 Mutating Primitives: `mkdirat` and `unlinkat`
Because POSIX `mkdirat` and `unlinkat` do not accept `open_how` resolution flags:
1. For multi-component path `a/b/c`:
   Open parent directory `a/b` via `openat2(dirfd, "a/b", open_how { flags: O_PATH | O_DIRECTORY | O_CLOEXEC, resolve: RESOLVE_BENEATH | RESOLVE_NO_XDEV | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_SYMLINKS })`.
2. Verify parent descriptor `parent_dfd`.
3. Dispatch single-component operation on `parent_dfd`:
   - `mkdirat(parent_dfd, "c", mode)`
   - `unlinkat(parent_dfd, "c", 0)` (file)
   - `unlinkat(parent_dfd, "c", AT_REMOVEDIR)` (directory)
4. Because the target is a single leaf component relative to an already-pinned directory descriptor, no intermediate traversal races are possible.

## 5. Windows Architecture (Feasibility Track & Formalized Design)

Windows Win32 subsystem (`CreateFileW`) does not provide an equivalent to `openat2(RESOLVE_BENEATH)`. `FILE_FLAG_OPEN_REPARSE_POINT` only inhibits dereferencing on the terminal pathname component, leaving intermediate components vulnerable to junction/symlink resolution races.

### 5.1 Native NT System Call (`NtCreateFile`) vs. Win32 Flags
The Windows containment spike operates directly on native NT system calls exported by `ntdll.dll`:
```rust
fn NtCreateFile(
    file_handle: *mut HANDLE,
    desired_access: u32,
    object_attributes: *mut OBJECT_ATTRIBUTES,
    io_status_block: *mut IO_STATUS_BLOCK,
    allocation_size: *mut i64,
    file_attributes: u32,
    share_access: u32,
    create_disposition: u32,
    create_options: u32,
    ea_buffer: *mut c_void,
    ea_length: u32,
) -> NTSTATUS;
```

#### Native NT Parameters (Decoupled from Win32 Subsystem Flags):
- `OBJECT_ATTRIBUTES.RootDirectory`: Verified parent `HANDLE`.
- `OBJECT_ATTRIBUTES.ObjectName`: Pointer to `UNICODE_STRING` containing **strictly a single path component** (zero slashes, colons, or traversal tokens).
- `OBJECT_ATTRIBUTES.Attributes`: `OBJ_CASE_INSENSITIVE (0x00000040)`:
  - *Native-API Behavioral Caveat & WSL Issue #3359*: While `OBJ_CASE_INSENSITIVE` is standard for Win32 subsystem compatibility, its interaction with `OBJECT_ATTRIBUTES.RootDirectory` inside per-directory case-sensitive parents is non-trivial. Public Microsoft kernel issue reports (such as WSL issue #3359) document that `NtCreateFile` with `OBJ_CASE_INSENSITIVE` can fail with `STATUS_OBJECT_NAME_NOT_FOUND` when casing diverges in a case-sensitive directory, and raise an unresolved question regarding how the kernel resolves lookups when multiple differently cased sibling names coexist (e.g., `foo` and `FOO`). `OBJ_CASE_INSENSITIVE` must never be assumed to guarantee deterministic selection among differently cased sibling names.
  - *Unified Fail-Closed Invariant*: Until comprehensive adversarial native-API test suites establish that supporting case-sensitive parent lookups is safe and deterministic, Plugxel enforces a strict, unified rule: **every parent directory possessing per-directory case sensitivity (`FILE_CS_FLAG != 0`) must be rejected fail-closed with `WASI_ENOTCAPABLE` (`76`)**; see Section 5.2 and Section 5.5.
- `CreateDisposition`: `FILE_OPEN (1)`, `FILE_CREATE (2)`, `FILE_OPEN_IF (3)`.
- `CreateOptions`:
  - `FILE_DIRECTORY_FILE (0x00000001)` for directories; `FILE_NON_DIRECTORY_FILE (0x00000040)` for files.
  - `FILE_OPEN_REPARSE_POINT (0x00200000)`: Native NT option ensuring reparse points (junctions, symlinks, mount points) are opened as reparse objects rather than dereferenced.
  - `FILE_SYNCHRONOUS_IO_NONALERT (0x00000020)`: Synchronous handle semantics.
  - `FILE_OPEN_FOR_BACKUP_INTENT (0x00004000)`: Native equivalent of backup semantics, enabling directory handle acquisition.

### 5.2 Component-by-Component Walking, Reparse Point & Pre-Open Case-Sensitivity Invariants
Because NT kernel path resolution resolves slashes internally when multi-component strings are passed, **multi-component path strings are strictly forbidden in `NtCreateFile` calls**.
Every pathname resolution walks strictly one component token at a time relative to a verified, pinned parent directory handle.

#### Mandatory Pre-Open Parent Inspection Order (Illustrated for `a/b/c`):
To satisfy fail-closed security invariants, parent directory case-sensitivity state must be inspected **prior** to resolving any child component beneath it. If `FileCaseSensitiveInformation` queries fail (requiring `FILE_READ_ATTRIBUTES`), or return indeterminate status, resolution immediately fails closed with `WASI_ENOTCAPABLE` (`76`) rather than assuming case-insensitivity:

1. **Lexical Tokenization & Validation**:
   Parse `rel_path` into single component tokens (`["a", "b", "c"]`). Reject empty tokens, `.`, `..`, `/`, `\`, `:`, wildcards (`*`, `?`), device names, and null bytes (`\0`).
2. **Pre-Open Inspection of `root_handle` (Parent of `a`)**:
   Query `FileCaseSensitiveInformation` on `root_handle`. If per-directory case sensitivity is active (`FILE_CS_FLAG != 0`) or the query fails/returns indeterminate status, fail closed immediately with `WASI_ENOTCAPABLE` (`76`).
3. **Open Component `a` Relative to `root_handle`**:
   Call `NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory = root_handle`, single component `"a"`, and `FILE_DIRECTORY_FILE | FILE_OPEN_REPARSE_POINT`.
   - Interrogate `h_a` via `GetFileInformationByHandle`:
     - If `dw_file_attributes & FILE_ATTRIBUTE_REPARSE_POINT (0x400) != 0` -> Close `h_a` and return `WASI_ENOTCAPABLE` (`76`).
     - If `dw_file_attributes & FILE_ATTRIBUTE_DIRECTORY == 0` -> Close `h_a` and return `WASI_ENOTDIR` (`54`).
4. **Pre-Open Inspection of `h_a` (Parent of `b`)**:
   Query `FileCaseSensitiveInformation` on pinned handle `h_a`. If case-sensitive (`FILE_CS_FLAG != 0`) or the query fails, close `h_a` and return `WASI_ENOTCAPABLE` (`76`).
5. **Open Component `b` Relative to `h_a`**:
   Call `NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory = h_a`, single component `"b"`, and `FILE_DIRECTORY_FILE | FILE_OPEN_REPARSE_POINT`.
   - Verify reparse point absence and directory attributes on `h_b`. Close intermediate handle `h_a`.
6. **Pre-Open Inspection of `h_b` (Parent of `c`)**:
   Query `FileCaseSensitiveInformation` on pinned handle `h_b`. If case-sensitive (`FILE_CS_FLAG != 0`) or the query fails, close `h_b` and return `WASI_ENOTCAPABLE` (`76`).
7. **Dispatch Leaf Operation `c` Relative to `h_b`**:
   Open terminal leaf `"c"` relative to pinned parent handle `h_b`. For file operations, verify reparse point absence, volume serial parity, and hard-link limits (`n_number_of_links <= 1`). Close parent handle `h_b`.

### 5.3 Hard-Link Containment Policy (`NumberOfLinks > 1`)
Hard links on NTFS share the underlying file object and MFT record without possessing reparse point attributes (`FILE_ATTRIBUTE_REPARSE_POINT` is false).
- **Vulnerability**: An adversary or pre-existing fixture creates a hard link inside `/data` pointing to an external host file (e.g. `C:\Windows\System32\...`). Opening the file inside `/data` modifies the external file object.
- **Formalized Policy**: On leaf file handles, query `ByHandleFileInformation.n_number_of_links`. If `n_number_of_links > 1`:
  Immediately close the handle and deny with `WASI_ENOTCAPABLE` (`76`).
- **Scope & Host Trust Boundary Limitation**:
  Rejecting `n_number_of_links > 1` detects and rejects existing multi-link files at the time of handle inspection. However, **this check alone does not prevent subsequent external hard-link creation** if an external host process creates an additional hard link to the file object after inspection completes.
  - *Host Trust Boundary Invariant*: Protection against subsequent external hard-link creation requires host filesystem access controls: unprivileged external actors on the host must not have write permissions to the `/data` directory tree. External host processes capable of mutating `/data` outside the guest WASM sandbox belong to the host Trusted Computing Base (TCB) / host environment security model and reside outside the guest capability sandbox boundary.

### 5.4 Truncation Semantics & Concurrency Analysis: `SetFileInformationByHandle(FileEndOfFileInfo)`
- **Spike Implementation**: `windows.rs` currently implements `SetFilePointer(leaf_handle, 0, null, FILE_BEGIN)` followed by `SetEndOfFile(leaf_handle)` after handle verification passes.
- **Concurrency Hazard of Shared File Pointer**:
  `SetEndOfFile` truncates at the current file pointer offset (`CurrentByteOffset` in the kernel `FILE_OBJECT`). While resetting the file pointer to 0 resolves sequential zero-byte truncation, sharing a handle across concurrent threads introduces a race condition: a concurrent seek or write on the same file object shifts the pointer between `SetFilePointer` and `SetEndOfFile`, yielding non-zero or indeterminate truncation sizes.
- **Architectural Decision for Production Integration**:
  Production integration mandates migrating from `SetFilePointer + SetEndOfFile` to `SetFileInformationByHandle` with `FileEndOfFileInfo` (`FILE_END_OF_FILE_INFO { EndOfFile: 0 }`):
  ```rust
  let mut eof_info = FILE_END_OF_FILE_INFO { EndOfFile: 0 };
  SetFileInformationByHandle(
      leaf_handle,
      FileEndOfFileInfo, // Class 6
      &mut eof_info as *mut _ as *mut c_void,
      size_of::<FILE_END_OF_FILE_INFO>() as u32,
  );
  ```
- **Handle Access Rights Requirement**:
  Calling `SetFileInformationByHandle` with `FileEndOfFileInfo` strictly requires the handle to be opened with write access (`GENERIC_WRITE` or `FILE_WRITE_DATA`). If a handle is opened read-only, `SetFileInformationByHandle` fails with `ERROR_ACCESS_DENIED`, mapped to `WASI_EACCES` (`2`). Production handle acquisition must explicitly gate truncation rights.
- **Boundary of Atomicity: Truncate vs. Concurrent Writes Across Descriptors**:
  `SetFileInformationByHandle(FileEndOfFileInfo)` sets the end-of-file mark directly on the underlying file object without referencing, depending on, or mutating the shared file pointer position, eliminating single-handle file-pointer positioning races. However, **this does NOT provide universal atomicity or race elimination for concurrent file operations**:
  1. *Open-Time Pre-Publication*: Synchronous truncation during `path_open(O_TRUNC)` ensures the newly issued descriptor is not exposed to guest threads until zeroing completes, preventing the calling guest thread from observing partial truncation.
  2. *Unsynchronized Cross-Descriptor Race Limitation*: If another active descriptor (opened previously by the guest runtime or a concurrent thread) already references the same underlying file object, WASI descriptor-table synchronization does **not** serialize byte stream I/O (`WriteFile` / `pwrite`) against `SetFileInformationByHandle`. A concurrent write from an existing descriptor during truncation can interleave, re-expand the file, or leave indeterminate data.
  3. *Unresolved Architectural Requirement (Open Gate)*: Cross-descriptor file-level serialization (e.g., file-level mutexes, byte-range locks, or exclusive share modes via `FILE_SHARE_READ`) is unproven in the current runtime and remains an explicit, open acceptance gate. The production integration must not claim intra-process cross-descriptor write-vs-truncate race immunity until verified with dedicated concurrency stress tests.

### 5.5 Volume Boundaries & Path Namespace Rejection
1. **Cross-Volume Traversal Rejection**:
   Compare `leaf_info.dw_volume_serial_number != root_info.dw_volume_serial_number`. Any mismatch indicates cross-device/volume traversal and immediately returns `WASI_ENOTCAPABLE` (`76`).
2. **Directory-Boundary-Aware Canonical Path Verification & Exact Ordinal Comparison Policy**:
   Interrogate `GetFinalPathNameByHandleW(handle, ..., FILE_NAME_NORMALIZED | VOLUME_NAME_DOS)` on both `root_handle` and `leaf_handle` to resolve the authoritative device volume and canonical path.
   - **Prefix & Separator Normalization**:
     Strip device namespace prefixes (`\\?\`, `\??\`). Normalize all forward slashes (`/`) to backslashes (`\`). *Never apply naive ASCII lowercase as a security normalization*.
   - **Hazard of Case-Insensitive Canonical Comparison**:
     While case-sensitive directories encountered *inside* the sandbox tree are rejected fail-closed during component walking (Section 5.2), **ancestor directories outside the sandbox root** may reside on NTFS volumes or directories with per-directory case sensitivity enabled. For example, if parent `C:\sandbox` is case-sensitive, `C:\sandbox\data` (sandbox root) and `C:\sandbox\DATA` (external directory) represent distinct sibling nodes. Evaluating canonical containment with case-insensitive comparison (`bIgnoreCase = TRUE`) would falsely equate `data` and `DATA`, allowing an external leaf to establish false canonical containment.
   - **Mandatory Exact Ordinal Component-Slice Comparison Algorithm**:
     To prevent ancestor case-confusion and eliminate substring prefix collisions (`C:\sandbox\data` vs `C:\sandbox\data-evil\secret.txt`):
     1. Decompose normalized canonical paths into component token vectors: `root_components` and `leaf_components` (via `std::path::Path::components()` or tokenizing on `\`).
     2. Length Precondition: If `leaf_components.len() < root_components.len()`, resolution has escaped root; immediately fail closed with `WASI_ENOTCAPABLE` (`76`).
     3. Exact Ordinal Component Evaluation:
        For each component index `i` in `[0, root_components.len())`:
        - Evaluate exact binary ordinal equivalence between `root_components[i]` and `leaf_components[i]`.
        - Slices of UTF-16 code units must be evaluated via direct slice equality (`root_slice == leaf_slice`) or via Win32 `CompareStringOrdinal(root_c_ptr, root_c_len, leaf_c_ptr, leaf_c_len, /* bIgnoreCase = */ FALSE) == CSTR_EQUAL` passing **explicit UTF-16 code-unit lengths**. Passing `-1` for lengths is strictly forbidden for non-NUL-terminated buffer slices.
        - If any prefix component fails exact ordinal matching, or if the canonical path cannot be established reliably, fail closed immediately with `WASI_ENOTCAPABLE` (`76`). Case-folding is never used to bridge casing divergence between root and leaf canonical representations.
     4. Target Boundary Classification:
        - *Root Directory Target*: If `leaf_components.len() == root_components.len()`, the target resolves directly to the root capability directory itself (valid target).
        - *Strict Child Invariant*: If `leaf_components.len() > root_components.len()`, every prefix component has matched with exact ordinal equivalence and the remainder represents an authentic child component, mathematically preventing sibling directory collisions (`"data"` vs `"data-evil"`).
     5. Indeterminate State Fail-Closed:
        If directory attributes or canonical paths cannot be determined reliably, comparison must fail closed with `WASI_ENOTCAPABLE` (`76`).
   - **Defense-in-Depth Role & Primary Containment Invariant**:
     Canonical path string verification via `GetFinalPathNameByHandleW` is strictly a secondary defense-in-depth safety check. The primary containment guarantee is enforced by component-by-component handle walking pinned to `OBJECT_ATTRIBUTES.RootDirectory`. Canonical string comparison does **not** prove full kernel-level atomicity or universal containment on its own; it verifies only that the normalized path resolved by the handle matches the intended root tree without prefix collision or ancestor casing divergence.
3. **Disallowed Windows Namespaces**:
   Strictly reject:
   - Rooted / Absolute paths (`/...`, `\...`, `[A-Za-z]:...`)
   - NT Device / Object paths (`\\.\...`, `\\?\...`, `\Device\...`, `\??\...`)
   - Alternate Data Streams (any token containing `:`)

### 5.6 Handle-Directed Atomic Mutations
- `unlink_file_beneath` and `rmdir_beneath` open target objects relative to verified parent handles with `DELETE` access and `FILE_OPEN_REPARSE_POINT`.
- Target handles are verified for reparse point absence, volume parity, and hard-link limits.
- Deletion is committed directly on the handle via `SetFileInformationByHandle` (`FILE_DISPOSITION_INFO_CLASS`, `DeleteFile = TRUE`).
- Closing the handle commits deletion, eliminating pathname resolution races during cleanup.

### 5.7 Host Trust Boundary & Platform Parity Policy
- **Absence of Kernel Atomic Confinement**: Windows NT does not have a kernel VFS primitive that atomically confines pathname resolution beneath an arbitrary directory handle during multi-component path lookup.
- **Component Walking Assurance**: Component handle walking + handle pinning + post-open verification provides robust defense-in-depth against guest-initiated TOCTOU and directory escapes, but does **NOT** provide identical mathematical atomicity to Linux `openat2(RESOLVE_BENEATH)`.
- **Parity Verdict**: Plugxel will **NOT** force a false unified abstraction. Platform capability differences will remain documented explicitly in `docs/SECURITY.md`.

## 7. Mandatory Acceptance Criteria (Dual-Platform Verification Gates)

A P1.5 implementation must satisfy the following verification gates before consideration for trunk:

1. **Standard In-Capability I/O**: Valid CRUD operations inside `/data` pass cleanly (`PASS`).
2. **Rooted & Traversal Rejection**: Rooted paths (`/`, `\`, `C:`) and `..` escaping root fail closed with `ENOTCAPABLE` (`DENY`).
3. **Symlink, Junction & Magic-Link Invalidation**: Traversing symlinks, NTFS junctions, or magic-links (`/proc/self/...`) fails closed (`DENY`).
4. **Safe Parent Open & Leaf Mutation**: Multi-component paths resolve parent safely and mutate single leaf without race (`PASS`).
5. **Multi-Component Outside Traversal**: `mkdir` / `unlink` attempting to traverse outside returns `ENOTCAPABLE` (`DENY`).
6. **Destructive Mutation Confinement & Zero-Byte Truncation**: `O_CREAT | O_TRUNC` racing across symlinks never damages outside sentinel; pre-existing files truncated on open are verified reduced to exactly zero bytes before write (`PASS`).
7. **Hard-Link Multi-Alias Policy & Concurrency Stress**: Files with multiple links are denied with `ENOTCAPABLE`; concurrent rename/mutation stress tests verify outside sentinels remain 100% intact (`PASS`).
8. **Primitive Inavailability Fail-Closed**: In environments where `openat2` returns `ENOSYS`, operations fail closed with `ENOTCAPABLE`, never falling back to unsafe path string checks (`FAIL-CLOSED`).
